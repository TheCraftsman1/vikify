# Firebase Party Room

Vikify 2.0.2 uses this project's Realtime Database for its default Party Room:

`https://vikify-95144-default-rtdb.asia-southeast1.firebasedatabase.app`

Google sign-in authenticates room operations. No Render service or Go server is
needed for the default rooms. Replay, preferences, and saved mixes remain in
Cloud Firestore; keep that database and its existing rules.

## Publish the prepared configuration

From PowerShell in `C:\Users\kanch\Desktop\Music_player`:

```powershell
npm.cmd install --global firebase-tools
firebase.cmd login
firebase.cmd hosting:sites:list --project vikify-95144
```

Confirm that the Hosting site `vikify` belongs to this project. If it is
missing, create it with `firebase.cmd hosting:sites:create vikify --project
vikify-95144`. If another project owns that site ID, select a site you own and
update the Hosting target, `VikifyLinks.HOST`, and Android manifest before a new
APK build.

Then publish the room rules and the existing share-link pages together:

```powershell
firebase.cmd deploy --only "database:party,hosting:share" --project vikify-95144
```

The database target maps to instance `vikify-95144-default-rtdb` and publishes
`party-database.rules.json`. Hosting publishes only `hosting/public`. This
command does not replace Cloud Firestore rules or upload private app files.

For manual console publishing, paste `party-database.rules.json` into **Realtime
Database → Rules**, then click **Publish**. These are JSON rules for Realtime
Database, not the Firestore rules language. Keep the database locked until the
prepared rules are published.

## Check the app

Install the signed 2.0.2 APK over the current app. On each device, sign in with
Google, open Party Room, and create/join the same six-character code. Share
links use `https://vikify.web.app/invite/CODE`; Firebase Hosting must be
published for those web links. Entering a room code directly uses only the
Realtime Database. Each device streams its own audio; no music files are
uploaded to Firebase.

Previously shared `vikify-95144.web.app` links remain accepted by the app.

## Behavior and access

- One Google account occupies one seat. Several devices using that account can
  listen together; leaving one device keeps the seat while another remains.
- Rooms support 2–10 account seats and a bounded 26-track queue. A host can
  restrict controls, remove a listener, or adjust capacity. Bans are enforced
  by database rules, not only by the app interface.
- A room code acts as an invitation capability for signed-in Google users.
  A user who knows an active code can read its room snapshot in order to join.
  Listing/searching the room collection and anonymous access are denied.
- Rules protect other members' identities, host privileges, seats, and queue
  limits. Fixed seats make deletions and capacity enforceable by RTDB rules.
- Presence is held separately from the queue. Account leases allow another
  member to take over after a missing host's 45-second grace period.
- Room operations use server-confirmed transactions. Playback/queue controls
  expire after 10 seconds and are not replayed indefinitely after reconnecting.
  Each state has a monotonic sequence and a timed playback anchor. Firebase's
  clock offset is an estimate; playback timing still needs a two-device audio
  check on the production network.
- Rooms stop accepting normal operations after 12 hours. The client does not
  physically garbage-collect every expired room; administrative retention can
  be added separately. No Cloud Functions or paid server instance is required
  by this implementation. Firebase plan connection and bandwidth limits apply.

## Verification

The local database emulator tests include unauthorized users, simultaneous
joins, seat limits, host-only controls, kicks, stale operations, queue bounds,
and native Android engine/codec payloads. Run from the repository root:

```powershell
npm.cmd --prefix docs/firebase/party-tests ci
npm.cmd --prefix docs/firebase/party-tests test
```

The optional native-payload test uses
`output/firebase-party-client-payloads.json`, generated by the Android
`FirebasePartyInteropTest` when `VIKIFY_PARTY_FIXTURE_OUTPUT` names that file.
Production Google-account access and two-device audio timing require the
published project configuration; local tests do not claim those are verified.
